\begin{abstract}
This report describes the development of DeliveryDispatch, a solution for
indexing restaurants and a synthetic courier fleet in Belo Horizonte. The
approach combines Geohash encoding, a compact Trie implemented as part of the
project, position generation using a normal distribution, and projection of
points onto the OpenStreetMap road network. In addition to the algorithmic
decisions, this report presents the data-preparation pipeline, the testing
strategy, and an experimental evaluation with six queries performed on a fleet
of 400 couriers.
\end{abstract}

\section{Introduction}

The proposed problem consists of building a geospatial search and monitoring
engine for a courier fleet operating in the city of Belo Horizonte. Given a
selected restaurant, the system must quickly locate candidate couriers, remove
those outside a service radius, and display the results on an interactive map,
together with distances and estimated arrival times \cite{enunciado}.

An exact search over the entire fleet would have a cost proportional to the
total number of couriers for every query. To reduce this search space, the
solution associates each position with a Geohash cell and uses prefixes of
those cells as keys in a compact Trie. Prefix selection yields a candidate set;
a subsequent geometric stage then accounts for adjacent cells and verifies the
actual distance to the restaurant. This combination seeks to balance indexing
speed with spatial accuracy.

The project was developed for Practical Assignment 1 in the course
DCC207 --- Algorithms 2. This document focuses on the technical description and
design decisions, while the repository README remains focused on installation
and execution.

\section{Architecture and data flow}

The implementation was divided into algorithms, models, data access, and
services. The main pipeline can be summarized as follows:

\begin{enumerate}
    \item read the provided bar and restaurant dataset;
    \item geocode addresses that are still pending;
    \item persist the enriched CSV and construct the domain objects;
    \item generate $N$ synthetic positions around the establishments;
    \item project those positions onto drivable roads;
    \item encode the coordinates as Geohashes;
    \item build the textual and geospatial indexes and display the points.
\end{enumerate}

\section{Geographic data preparation}

\subsection{Reading and persistence}

The loader validates the presence of the required columns and converts each row
into a \texttt{Bar} object. The processed CSV adds latitude, longitude, and
\texttt{GEOCODING\_STATUS}; the Geohash is calculated in memory when the record
is loaded and is therefore not duplicated in the file.

Persistence uses a temporary file that is subsequently moved to replace the
destination file.
This procedure reduces the risk of leaving a partially written CSV if an
interruption occurs. During a geocoding run, checkpoints are also saved every
100 queries. Records with the \texttt{found} or \texttt{not\_found} status are
not queried again, allowing processing to resume for items still marked as
\texttt{pending}.

\subsection{Geocoding and cache}

The Nominatim client sends requests sequentially, identifies the application
with a \emph{User-Agent}, limits the rate to one request per second, and
maintains a local JSON cache. These measures reduce repeated queries and comply
with the main restrictions of the public service \cite{nominatim-policy}. The
cache is not version-controlled.

\section{Algorithms and design decisions}

\subsection{Geohash encoding}

The implementation begins with the intervals $[-180,180]$ for longitude and
$[-90,90]$ for latitude. Each bit bisects one of the intervals. Even-indexed
bits refine longitude and odd-indexed bits refine latitude, so interleaving
begins with longitude. After every five binary decisions, the resulting value
selects a character from the Geohash Base32 alphabet.

For a precision of $p$ characters, $5p$ subdivisions are performed. Thus,
encoding time and space are $O(p)$; in this project, $1 \leq p \leq 8$.
Decoding follows the reverse path and returns the center of the represented
cell. As a scale reference, at the equator an eight-character cell measures
approximately $38.2\,\mathrm{m} \times 19\,\mathrm{m}$, with dimensions that
vary according to latitude \cite{elastic-geohash-grid}.

Geohash provides a spatial approximation, not a metric distance. Furthermore,
nearby points may fall into different cells when they lie on opposite sides of
a boundary.

\subsection{Compact Trie}

The Trie was implemented within the project, without off-the-shelf libraries
for the core data structure. Each node stores the full segment of the edge that
connects it to its parent rather than a single character. Children are kept in
a dictionary indexed by the edge's first character. A special leaf identified
by \texttt{\$} marks the end of the key and stores a generic value. This choice
is based on the prefix-tree model discussed in class, adapted here to compress
paths without branching \cite{aula-trie}.

Insertion has three main cases: creating a new edge, continuing along a fully
matching edge, or splitting the edge at the longest common prefix. Removal
performs the inverse process and rejoins paths left with a single nonterminal
child. This mechanism reduces chains of nonbranching nodes.

The search consumes the prefix along the compressed edges and, after a match,
collects the leaves of the subtree. Assuming constant average-time access to
the child dictionary, navigation costs $O(m)$, while materializing the results
costs the number of nodes visited. Under the expected contract, this is
expressed as $O(m+k)$, where $m$ is the prefix length and $k$ represents the
number of results returned.

\subsection{Text search: indexes and substring fallback}

Restaurant trade names, legal names, and addresses are normalized by converting
them to lowercase, applying Unicode decomposition, removing accents, and
collapsing whitespace sequences. Two separate Tries receive these texts and
their respective \texttt{Bar} objects: one indexes trade and legal names; the
other indexes the full address. A unique internal suffix prevents records with
identical text from overwriting one another. The query first traverses both
Tries and removes duplicates by identifier, so prefix matches are returned with
priority.

A prefix-only search, however, does not cover common inputs such as
``Portugal'' for ``Avenida Portugal'' or ``Centro'' when the neighborhood
appears in the middle of the address. Therefore, after the indexed stage, the
service performs a substring fallback: it scans establishments not yet
returned and checks whether the normalized query occurs anywhere in the trade
name, legal name, or address. The same result limit is enforced during both
stages.

This design avoids inserting every word and every text suffix into the Trie,
which would increase the index size and construction complexity. The trade-off
is that, in the worst case, the fallback performs a linear scan of the $B$
establishments, in addition to the cost of substring comparisons. The
interface reduces the practical impact by requiring at least two characters,
returning at most 12 suggestions, and placing Trie results first.

\section{Geospatial search and filtering}

Each courier is inserted into a compact Trie using its full eight-character
Geohash. An internal suffix containing the record position makes each key
unique, so several couriers can occupy exactly the same cell without one value
replacing another.

For each query, the specified radius dynamically determines the grid precision
$p$. The greatest precision from 1 to 8 whose approximate cell height and width
at the query latitude are both at least as large as the radius is selected. For
a local search, this choice limits coverage to the
restaurant's cell and, at most, its eight immediately adjacent cells. The
routine calculates the circle's bounding rectangle and enumerates every prefix
that intersects it; for exceptionally large radii, the enumeration is expanded
instead of assuming only nine cells. Consequently, a nearby courier is not
missed when a Geohash boundary separates the two points.

Each prefix is queried in the Trie, and the leaves of the corresponding
subtrees form the candidate set. Given $c$ queried cells, prefixes of length
$p$, and $k$ candidates, this stage costs $O(cp+k)$. Since $p\leq 8$ and, for
local searches, $c\leq 9$, the grid terms are bounded by small constants. In
the interface, the index built for a fleet is reused until a new generation
replaces the couriers.

The grid is only a spatial approximation: all candidates therefore undergo the
exact Haversine test. For latitudes $\varphi_1,\varphi_2$, latitude difference
$\Delta\varphi$, and longitude difference $\Delta\lambda$, the calculation is

\begin{align}
a &= \sin^2\left(\frac{\Delta\varphi}{2}\right)
  + \cos(\varphi_1)\cos(\varphi_2)
    \sin^2\left(\frac{\Delta\lambda}{2}\right), \\
d &= 2R\arcsin(\sqrt{a}),
\end{align}

with $R=6\,371.0088\,\mathrm{km}$. Only couriers whose $d$ is less than or equal
to the requested radius are included in the final result. Filtering costs
$O(k)$ and removes the false positives introduced by the rectangular cell
coverage.
The adopted formulation follows the definition of great-circle distance
documented by scikit-learn \cite{haversine-sklearn}.

\subsection{Arrival-time estimate}

The assignment requires the distance to be accompanied by an estimate of the
time to reach the restaurant. Because the system neither calculates routes nor
receives each courier's instantaneous speed, a constant average speed of
$30\,\mathrm{km/h}$ was adopted. For a distance $d$ calculated with the
Haversine formula, the value displayed in the table is

\begin{equation}
t_{\mathrm{min}} = \frac{d}{30}\,60.
\end{equation}

This decision keeps the calculation simple, deterministic, and sufficient for
the simulation. The value should be interpreted as a straight-line
approximation: traffic, traffic lights, terrain, and actual route length are
not considered. A future extension could replace this approximation with the
shortest path in the road graph and speeds associated with each segment.

\section{Synthetic courier generation}

The fleet is generated only from establishments with coordinates. After a
reproducible shuffle of the centers, the $N$ couriers are assigned to
restaurants in round-robin order. Consequently, the difference between the
numbers associated with any two centers used is at most one.

For each courier, two independent offsets are drawn,
$X,Y \sim \mathcal{N}(0,\sigma^2)$, with $\sigma=500\,\mathrm{m}$
\cite{normal-nist}. The offsets are approximately converted from meters to
degrees using

\begin{align}
\Delta\varphi &=
    \frac{X}{111\,320}, \\
\Delta\lambda &=
    \frac{Y}{111\,320\max\left(|\cos\varphi|,10^{-12}\right)},
\end{align}

where $\varphi$ is the restaurant's latitude. The cosine correction compensates
for the varying length of one degree of longitude. In the service, the default
seed is 42, which allows the same draws to be repeated in tests and
programmatic calls. In the dashboard, the button click counter is used as the
seed: each new generation produces a different simulation, but the result
remains deterministic for the same input, restaurant order, and counter value.

The mathematical generation has a cost of $O(N)$, excluding road-network
projection. After that projection, each courier receives a sequential
identifier, the corrected coordinates, the identifier of the restaurant used
as its center, and its Geohash.

\section{Road-network correction}

Points produced by a continuous distribution may fall inside buildings, city
blocks, or bodies of water. To approximate valid positions on the road network,
the road-network service uses OSMnx and OpenStreetMap data
\cite{osmnx-docs,osm-copyright}.

On the first run, the simplified driving-network graph for Belo Horizonte is
obtained (\texttt{network\_type=drive}). The graph is projected into a
coordinate system suitable for metric operations and saved as GraphML. This
file is reused on subsequent runs.

The synthetic coordinates, initially in EPSG:4326, are converted to the graph's
coordinate system. OSMnx finds the nearest edge to each point. The geometry
library then interpolates the position along that edge, and the result is
converted back to EPSG:4326. When an edge has no explicit geometry, the segment
between its start and end nodes is used as an approximation.

The map data are made available by OpenStreetMap under the ODbL license and require
attribution to the project and its contributors
\cite{osm-copyright}.

\section{Interactive interface}

The application provides a web dashboard built with Dash and Plotly. The
dashboard keeps the controls in a side column and reserves most of the screen
for the OpenStreetMap basemap. The layout is responsive, so on narrow screens
the controls appear above the map.

The restaurant field queries the dataset on demand by trade name, legal name,
or address. Inputs are normalized without regard to case or accents; queries
shorter than two characters are not executed, and at most 12 suggestions are
sent to the browser. Prefix search in the Tries is complemented by the
substring fallback described previously. When a geocoded result is selected,
the map is centered on the establishment and highlights it in a color distinct
from the fleet.

The user enters the number $N$ and explicitly triggers generation. The
callback validates that the value is a nonnegative integer, performs the
generation, and replaces the session's previous state with the new couriers.
Points are sent to the browser in a serializable format and displayed in an
aggregated graphical layer without creating one interface component per marker.
After a query, couriers accepted by the filter are highlighted in green, while
the others remain gray. Restaurants are displayed in gray, except for the
selected restaurant, which is highlighted in orange. The interface presents
the number of couriers found as a summary metric. The table details each
result's identifier, distance, estimated time, coordinates, and Geohash, sorted
by distance and, in the event of a tie, by identifier. During the calculation,
the button remains disabled; failures when loading or querying the road network
are displayed within the dashboard without erasing the last valid fleet.

\section{Testing and quality assurance}

The automated tests verify the contracts of both isolated components and the
orchestration layer. The covered scenarios include:

\begin{itemize}
    \item known values and invalid inputs in Geohash encoding;
    \item Trie insertion, edge splitting, search, removal, and values;
    \item reading, persistence, and resumption of the processed CSV;
    \item querying and reusing the geocoding cache without real network access;
    \item balance and reproducibility in courier generation;
    \item projection onto an edge of a synthetic graph;
    \item normalization, duplicates, limits, and substring fallback in text
    search;
    \item adjacent-cell coverage and Haversine filtering;
    \item control validation and interactive map composition;
    \item integration of the main pipeline using controlled test doubles.
\end{itemize}

Protocols for the geocoder and road-network projector allow fake
implementations to be used in tests, keeping the domain logic independent of
network access. Continuous integration runs static analysis, formatting checks,
tests, and package builds with Python 3.12 on Linux and Windows. In the final
local verification, all 69 automated tests passed.

\section{Experimental evaluation}

\subsection{Methodology}

The experiment was run locally with a single fleet of 400 couriers. The fleet
was held fixed across all queries so that variation in the number of results
would be caused only by the selected restaurant and radius. Pizzaria Guarani
and Rei do Pastel were selected, and radii of $0.5$, $2.0$, and
$5.0\,\mathrm{km}$ were evaluated for each. Before the measurements, the
application and road network were already loaded; therefore, the timings do not
include the initial OpenStreetMap download or fleet generation.

Time was measured with \texttt{time.perf\_counter} in the callback triggered by
a change in the restaurant or radius. Measurement starts upon entering the
callback and ends after the geospatial search, table construction, and map
figure preparation. It therefore represents server-side application processing
time but excludes response transport and final browser rendering. Each row in
Table~\ref{tab:experiments} corresponds to a query also recorded in
\path{experiments/results/consultas.csv}.

\section{Conclusion}

DeliveryDispatch fulfills the proposed pipeline: it prepares the restaurant
dataset, generates a synthetic fleet concentrated in demand regions, snaps
positions to the road network, indexes couriers in a compact Trie, and combines
approximate Geohash search with exact Haversine filtering. Geohash encoding and
the Trie were implemented directly, while external libraries were reserved for
the interface, cartographic projections, and OpenStreetMap access.

The main decisions sought to balance correctness and simplicity: adjacent cells
prevent false negatives at Geohash boundaries; the unique suffix preserves
couriers in the same cell; the normal distribution approximates demand regions;
the cache reduces repeated access to external services; and the average speed
of $30\,\mathrm{km/h}$ provides an explicit and reproducible arrival estimate.
Across the six experimental scenarios, the interface returned between 3 and
115 couriers, with processing times ranging from $721.7$ to
$925.1\,\mathrm{ms}$. The results and automated tests support the functional
correctness of the solution, while real routing and an evaluation with repeated
measurements remain possible improvements.
